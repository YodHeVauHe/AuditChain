# AuditChain Procurement MVP — Design

Date: 2026-09-05
Status: Approved for implementation planning

## Purpose

Build the procurement MVP promised in the pitch deck (`PitchDeck/`, slides 6, 8, 11, 18–20): a permissioned ledger that holds cryptographic commitments to procurement events, with a console that lets a procurement officer commit events and an auditor verify them.

The MVP's primary job is a **TES validation demo**: a working multi-node demonstration with tamper-detection scenarios, shown to auditors, procurement and compliance stakeholders to support the TES/MIIC ask. Demo polish and the tamper-detection storyline matter more than production hardening.

## Decisions made during brainstorming

| Question | Decision |
| --- | --- |
| Primary purpose | TES validation demo |
| Node language | Rust, matching slide 11 |
| Multi-node | 3 nodes, leader proposes, peers ack, commit at 2/3 quorum — no full BFT |
| Interaction surface | Next.js web console with Procurement and Auditor roles |
| Evidence | Uploaded files stored off-chain in the console; SHA-256 committed to ledger; re-hash to verify |
| Anomaly detection | Deterministic sequencing + integrity rules computed on read |
| Seed data | Pre-seeded synthetic slide-8 lifecycle, committed through the real API |
| Deadline | None fixed; build in dependency order |

## Goals

- Every slide-11 claim literally true in the running demo: SHA-256 evidence commitments, Ed25519 signatures under an institutional identity, permissioned validator set, chained blocks, multi-node replication, no cryptocurrency/mining/public chain.
- A one-command demo (`docker compose up`) with a pre-seeded lifecycle including the deliberate payment-before-contract anomaly from slide 8.
- Live tamper detection: edit one node's stored history, watch its self-check fail and its copy diverge from the other two.
- Evidence verification that stakeholders can perform themselves: re-hash a file, compare against the ledger commitment.

## Non-goals (MVP)

- Real BFT/Raft consensus; fixed leader is acceptable.
- Authentication/authorisation for console users (single-institution demo; roles are views, not accounts).
- Any production deployment, monitoring, or upgrade story.
- Institutions other than one seeded demo institution.
- The deck itself remains untouched.

## Architecture

Four processes, orchestrated by docker-compose. Ports: nodes listen on 7001–7003, console on 3000.

- `node1`, `node2`, `node3` — three instances of one Rust binary, `auditchain-node`. Each holds only commitments: blocks, events, signatures, hashes. Per-node SQLite storage.
- `console` — Next.js App Router app. The "institution side": off-chain evidence store (files on a mounted volume + metadata in its own SQLite), the institution's Ed25519 private key, and both role views. It submits signed events to a node's HTTP API and reads chains from any node.

The boundary is architectural, not notional: evidence bytes never reach a node; only hashes and signatures cross.

## Node design (`node/` — Rust crate)

Single crate, two binaries: `auditchain-node` (the server) and `tamper-demo` (dev-only, see Tamper detection).

Configuration via environment: node id, HTTP listen port, peer list, validator key path, SQLite path, institution public key path.

### Data model

- **Event:** `ref` (e.g. `CON-2026-0455`), `type` (one of `budget_created`, `procurement_started`, `bid_received`, `bid_evaluated`, `supplier_selected`, `contract_approved`, `payment_made`), `title`, `actor`, `occurred_at`, optional `amount` (integer minor units), `evidence` (list of `{filename, sha256}` hex), `institution_signature` (Ed25519 over the canonical event JSON, i.e. the event without the signature field).
- **Block:** `height`, `prev_block_hash`, `events_hash` (SHA-256 over the canonical concatenation of the block's canonical event JSONs), `committed_at`, `leader_signature` (over the block header), `certificate` (leader + quorum acks: validator signatures over the header hash).
- **Canonical JSON:** keys sorted lexicographically, no insignificant whitespace, UTF-8. Hashes are SHA-256, hex-encoded. All signing and hashing operates on canonical form so results are deterministic.
- **Node storage (SQLite):** `blocks`, `events` (indexed by `ref`), `meta` (head height, head hash). Block hash chains each block to its predecessor.

### Keys

- Each node has an Ed25519 validator keypair, generated by `auditchain-node keygen` during setup and persisted at the configured path.
- The institution keypair is generated once during seeding; the private key is mounted into the console, the public key into every node.

### HTTP API

Public (used by console and auditors):

- `POST /events` — submit a signed event. Admitted into the next block if valid.
- `GET /chain` — full chain (blocks + events) from genesis.
- `GET /events/{ref}` — event lookup with its block position.
- `GET /integrity` — self-check: recompute every hash chain link, re-verify institution and leader signatures across all blocks; returns per-block ok/fail verdicts.

Internal (node-to-node, on the same port under `/internal`):

- `POST /internal/block` — leader proposes a signed block to peers.
- `POST /internal/ack` — peer's signed acknowledgement of a valid proposal.
- `POST /internal/commit` — leader broadcasts the commit certificate.
- `GET /internal/status` — height, head hash, node id (used by console for cross-node comparison and health).

### Consensus (simple quorum)

- Leader is fixed: node 1. On event admission the leader forms a block (next height, prev hash, event list), signs the header, and sends it to both peers.
- A peer validates: institution signature on each event, chain link against its own local head, leader signature. Valid → acks with its validator signature over the header hash. Invalid → rejects with a reason.
- At 2 of 3 acks (leader's own counts as one), the block is committed; the leader broadcasts the certificate so all nodes end with identical blocks.
- With one peer down, quorum of 2 is still reachable and commits proceed. If the leader is down, no commits occur (console surfaces this); reads are unaffected. This is an accepted MVP limitation.

### Admission control

Nodes reject, with explicit reasons: invalid institution signature, malformed event (unknown type, missing fields, bad sha256 format), and duplicate `ref`. Duplicate refs are therefore an integrity guarantee at the boundary. Ordering violations are **not** rejected at admission — they are process anomalies to surface, not integrity violations (see Anomaly rules).

## Console design (`console/` — Next.js)

Two role views, echoing the deck's dark/gold styling lightly but built as a working tool.

### Procurement view

- Lifecycle dashboard over the committed chain.
- Commit form: stage type, ref, title, actor, occurred date, optional amount, evidence file upload (multiple files per event).
- On submit: server computes SHA-256 per file, stores files in the evidence store (volume) + metadata (its SQLite), signs the canonical event JSON with the institution key, POSTs to the leader node, and displays the returned receipt: event hash, block height, commit certificate. If no quorum, the event is shown as pending with reason.

### Auditor view

- Timeline of the lifecycle (slide-8 style) with anomaly flags inline.
- Event drill-down: full event detail, evidence list, block position, signatures.
- **Evidence verification:** for any event, re-hash a file — either the stored original (expected match) or a freshly uploaded file (e.g. a doctored version, expected mismatch) — and compare against the event's committed evidence hashes. Shows both hashes side by side.
- **Chain verification:** run `GET /integrity` against any chosen node and show per-block verdicts; the node selector defaults to the leader but the auditor can point at node 2 or 3 — "don't trust the proposer" is a one-click demo moment.
- **Cross-node comparison:** fetch `/internal/status` from all three configured nodes and compare head height and head hash per node; report any divergence.

Console configuration via env: `AUDITCHAIN_NODES` (comma-separated node URLs), `INSTITUTION_KEY_PATH`, `EVIDENCE_STORE_PATH`, `CONSOLE_DB_PATH`.

## Anomaly rules (computed on read)

A pure TypeScript module in the console evaluates the committed chain and returns typed findings `{ruleId, severity, eventRef, explanation}`. Never stored; recomputed from the ledger.

- **R1 ordering violation:** an event was committed while its required predecessor is absent from the chain, or the predecessor's `occurred_at` is later than this event's. Required predecessor map: `procurement_started` → `budget_created`; `bid_received` → `procurement_started`; `bid_evaluated` → `bid_received`; `supplier_selected` → `bid_evaluated`; `contract_approved` → `supplier_selected`; `payment_made` → `contract_approved`.
- **R2 missing required stage:** an event committed with no occurrence of its required predecessor anywhere in the chain.

The seeded PAY-2026-0123-before-CON-2026-0455 event is a *process* anomaly caught by R1 — chain integrity remains perfect. This distinction (process anomaly ≠ integrity failure) is preserved explicitly in the UI copy.

## Tamper detection — the showpiece

Three independent mechanisms: per-node integrity self-check, cross-node chain comparison, and evidence re-hash.

`tamper-demo` is a dev-only binary in the node crate that opens a node's SQLite file directly (the honest attacker model: someone with access to one machine's storage) and alters a committed event — by default, changes `PAY-2026-0123`'s amount. Afterwards:

- That node's `GET /integrity` fails on the affected block (event no longer matches `events_hash`).
- Cross-node comparison reports divergence at that height.
- The other two nodes remain internally consistent — replication is the safety net.

## Seed data

Seeding is a subcommand of the Rust binary, `auditchain-node seed`, so canonical JSON and Ed25519 signing reuse the crate's own code rather than being re-implemented in a second language. It brings the demo to its opening state:

1. Generate validator keys (3), the institution keypair, and write configs.
2. Commit the slide-8 lifecycle through the real `POST /events` API — never direct DB writes — so all signatures and chain links are genuine: BUD-2026-0031, PR-2026-0117, BID-2026-0089, EVAL-2026-0064, SEL-2026-0058, CON-2026-0455, PAY-2026-0123, with each event's `occurred_at` matching the slide dates (04 Feb → 14 Mar) so PAY precedes CON.
3. Attach small synthetic evidence files (e.g. a memo PDF, an evaluation sheet) to key events.
4. Finish by running a full verification pass and printing the expected state: chain verified on all nodes, one R1 anomaly present.

## Error handling

- Console → node failures: surfaced in the UI with reason and "try another node" (node selector is always available).
- No quorum: event shown as pending; retry is manual (re-submit from the form).
- Malformed/unsigned/duplicate submissions: node rejection reasons are displayed verbatim in the console — rejection transparency is itself a demo beat.
- Leader down: console shows "leader unreachable — commits unavailable; reads unaffected".

## Testing

- **Rust unit tests:** canonical JSON, hashing, signature round-trips, chain validation, admission rules.
- **Rust integration test:** spawn an in-process 3-node cluster on ephemeral ports; commit events; assert quorum commit and identical chains; kill one peer and assert commits still succeed; tamper one node's store via the same code path as `tamper-demo`; assert its integrity check fails and cross-node comparison diverges.
- **Console unit tests (vitest):** anomaly rules engine (R1/R2) over fixture chains, including the seeded scenario.
- **Seed verification:** the seed command ends with a full verify pass and fails loudly if the expected state (verified + exactly one R1 anomaly) is not met.

## Build order

1. Node core: canonical JSON, hashing, signing, event/block model, single-node commit + read + integrity APIs.
2. Quorum replication across 3 nodes + docker-compose.
3. Console procurement flow (evidence store, signing, commit, receipt).
4. Console auditor view (timeline, evidence verification, chain verification, cross-node comparison) + anomaly rules engine.
5. Seed data, `tamper-demo`, end-to-end demo script and README.
